# 0. 这是什么

2026-11-04 处理 mes-app-mobile 接口忽快忽慢事故（根因 0.4 核 CFS 限流）+ 同日全集群配额治理时用到的全部命令，按排查阶段整理。命令通用，示例输出全部来自当时的真实现场（pod 名 nh2f8/xnpqb、服务名 assist/auth/produce、节点 work01/work02），换到任何项目改个命名空间就能用。叙事版复盘见 {% post_link "接口忽快忽慢的元凶是CPU限流——一次K8s-CFS排查复盘" "接口忽快忽慢的元凶是CPU限流——一次K8s CFS排查复盘" %}。

适用症状：容器内服务"慢但宿主机闲"、同一接口时快时慢、双副本一个忙死一个闲死、几十线程全 R 态但单线程 %CPU 极低。

# 1. 定性三件套：先看 cpu.stat

进目标 pod 第一时间跑（cgroup v1 路径；v2 在 `/sys/fs/cgroup/cpu.stat`）：

```bash
kubectl exec -it <pod> -- cat /sys/fs/cgroup/cpu/cpu.stat
```

事故现场真实输出对比（同一 deployment 双副本）：

```text
慢 pod nh2f8:                      快 pod xnpqb:
nr_periods 6959058                 nr_periods 6952914
nr_throttled 2697487               nr_throttled 96200
→ 38.8% 周期被冻                   → 1.38%
```

判读规则（只认一个比率）：

| 字段 | 含义 | 注意 |
|---|---|---|
| nr_periods | 经历的 100ms 调度周期数 | 695 万周期 ≈ 运行 8 天，可反推服务寿命 |
| nr_throttled | 配额烧穿、整组冻结的周期数 | **`nr_throttled/nr_periods` 是唯一判读指标** |
| throttled_time | 冻结累计时长 | ★所有被冻线程等待时长的**总和**，除回 nr_throttled 得不出"单次冻多久"（见过 11 次限流累计 353s 的样本） |
| nr_periods == 0 | **无配额，不记账** | 该容器根本没设 CPU limit，第三档状态，别当异常 |

再确认配额数值：

```bash
kubectl exec -it <pod> -- sh -c 'cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us /sys/fs/cgroup/cpu/cpu.cfs_period_us'
# 40000
# 100000   → 40000/100000 = 0.4 核
# cfs_quota_us = -1 → 无配额（iot、eureka 这类 StatefulSet 就是无配额档）
```

# 2. 实时差分：现在还在不在冻

cpu.stat 是生命周期累计值，老 pod 的均值会被摊平。要看"当前"状态用差分循环：

```bash
kubectl exec -it <pod> -- sh -c '
while :; do
  a=$(awk "/nr_throttled/{print \$2}" /sys/fs/cgroup/cpu/cpu.stat); sleep 1
  b=$(awk "/nr_throttled/{print \$2}" /sys/fs/cgroup/cpu/cpu.stat)
  echo "$(date +%T) +$((b-a))"
done'
# 正常：持续 +0；被限流：每秒跳几个到几十个
```

换算：**次/分 ÷ 600 = 当前被冻周期占比**。事故时 assist 差分 37.4 次/分 ≈ 当前 6.2% 周期被冻，比生命周期均值 4.36% 还差——说明它在恶化不是好转。

验收口径：调大 limit 后新 pod `nr_throttled=0` 只算开局干净，要拿这个循环跑满一个业务高峰时段、增量持续为 0 才算稳。

# 3. 容器内 JVM 取证（没有 jcmd/jstat 时）

JRE 精简镜像常见情况。四条路全部只依赖 /proc 和信号：

```bash
# ① JDK 可能装了只是没进 PATH——java 进程在跑，顺着 exe 链接找它的 bin 目录
JB=$(dirname $(readlink -f /proc/<pid>/exe))
ls $JB | grep -E 'jcmd|jstack'
$JB/jstack <pid> | grep -A 25 -i 'RxComputation'

# ② 兜底：SIGQUIT 只触发线程 dump 不会杀进程，输出进进程 stdout
kill -3 <pid>
kubectl logs <pod> --tail=800 | grep -B2 -A25 -i '线程名'

# ③ 纯 shell 排线程 CPU：/proc/<pid>/task/*/stat 字段14+15 = utime+stime（tick，100 tick ≈ 1s）
for d in /proc/<pid>/task/*; do awk '{print $14+$15, $2}' $d/stat 2>/dev/null; done | sort -rn | head -15

# ④ 看 JVM 启动参数（堆大小、GC 类型、是否感知容器配额）
tr '\0' ' ' < /proc/<pid>/cmdline; echo
```

④ 的附加价值：老 Java 8 未开 `UseContainerSupport` 时 GC 按宿主机核数开并行线程，几十个 GC 线程挤在 0.4 核配额里等于给限流添柴，补 `-XX:ActiveProcessorCount` 能显著缓解突发打穿。

找 pid 的方式：容器里一般就一个 java 进程，`ls /proc | grep -E '^[0-9]+$'` 逐个 cat cmdline，或直接 `top` 看。

# 4. top 的两个坑

```bash
top -Hp <pid>
```

- **TIME+ 是"分:秒"不是"时:分"**。事故里把线程累计 CPU `525:14.37` 误读成 525 小时（折算常年独占 2.7 核），方向带偏到"RxJava 空转烧 CPU"；实际是分:秒 = 8 小时 45 分，只占 0.045 核。单位核对先于归因。
- **几十线程全 R 态 + 单线程 %CPU 只有 0.6~2.5%** = 被 cgroup 冻住的典型形态，看到这个组合别再去查业务代码。

# 5. 全集群扫描（铺到所有 pod）

```bash
# 拿 pod 清单——★必须对总数，exec 静默失败会把漏报伪装成"无限流"
kubectl get pods -o wide --no-headers | awk '{print $1}' | wc -l

# 逐 pod 读（生命周期占比 + 5 分钟差分双指标）
for p in $(kubectl get pods --no-headers | awk '{print $1}'); do
  echo "== $p"
  kubectl exec $p -- cat /sys/fs/cgroup/cpu/cpu.stat 2>/dev/null || echo "  exec 失败！"
done
```

三条铁律：

1. **exec 失败必须显式打标**。首轮扫描 auth 就是被静默失败吞掉漏报的（报了 exec 成功列表里没它，险些漏掉一个 98 天慢性限流 2.31% 的服务）。
2. **判读三档**：有限流 / 无限流 / **无配额（per==0）**。用 `if(per>0)` 过滤"异常"会让无配额 pod 在扫描结果里静默消失，一度怀疑 exec 挂了或 cgroup v2——其实是 cfs_quota_us=-1 的 cgroup 根本不做周期记账。
3. **StatefulSet 天然漏网**：`kubectl get deploy` 批量清单不含 sts。识别特征：pod 名以 `-0`/`-1` 序号结尾（如 iot-0、eureka-0）而非随机哈希。

当时扫出来的全景：assist 4.36%（差分 37.4 次/分，最重）、auth 2.31%（慢性 98 天）、produce 1.2%~1.4%、业务服务 0.7%~1.3%、txmanage/gateway ≈0。

# 6. 用量实测：cpuacct.usage 差分

metrics-server 缺失（`kubectl top` 报 heapster NotFound）时的替代方案，cgroup 自带、零依赖：

```bash
kubectl exec <pod> -- cat /sys/fs/cgroup/cpu/cpuacct.usage   # 累计 CPU 纳秒
# 隔 300s 再读一次，差值 ÷ 300e9 = 平均核数
```

实测结果颠覆直觉：全集群 21 pod 合计只用 **~0.4 核**（assist 0.067 最高、produce 0.031、auth 0.018），每服务均值不到自身配额 20%，却仍高频限流——**均值数据永远看不见限流，限流看突发**。auth 是极端样本：均值最低档但单请求 token 校验 CPU 尖锐，突发/均值比全集群最高。

这套差分同时是**调大 limit 的安全性证据**：实际总用量 0.4 核 vs 宿主机 92% idle，放宽零容量风险。

# 7. k8s 侧查账与治理

## 7.1 节点容量账本

```bash
kubectl describe node work01 | sed -n '/Allocated resources/,/Events/p'
```

当时两台 work 节点（各 ~6 核可分配）：work01 request 占用 67%（余 1.9 核）、work02 87%（余 0.75 核，基本满）；limit 超卖 340%/365%——纸面数字，实际总用量 0.4 核，无碍。

## 7.2 调整配额

```bash
# 重点服务（request + limit 一起写！）
kubectl set resources deploy/mes-app-assist -n <ns> --requests=cpu=500m --limits=cpu=4
# 一般业务
kubectl set resources deploy/mes-app-produce -n <ns> --limits=cpu=2
# 观察滚动
kubectl rollout status deploy/mes-app-assist -n <ns>
```

★**只写 limit 不写 request 的默认值坑**：k8s 把缺省 request 默认成 limit 值。当时 datasync 只补 `--limits=cpu=2`，Pod 按 2 核参与调度占位，在 allocatable 紧张的节点上直接 Pending 卡了 21 分钟（describe pod 的 Events 里 `2 Insufficient cpu`），修复就是补 `--requests=cpu=300m`。资源要写就写全。

★**Pending 诊断**：

```bash
kubectl describe pod <pod> | sed -n '/Events/,$p'
# 看 Insufficient cpu 是哪个节点、surge 模式下老 pod 是否还在服务（未断流）
```

★**StatefulSet 改配额**：`kubectl set resources sts/<name>` 可用，但老集群 sts 常配 OnDelete 更新策略——改完模板不自动滚动，要手动删 pod 才生效。iot 这种 sts 且 request/limit 双空的是 BestEffort QoS：不会被限流（无配额）、也无需治理，代价是节点内存压力下最先被驱逐。

## 7.3 配额盘点（治理前先摸底）

```bash
kubectl get deploy -n <ns> -o custom-columns='NAME:.metadata.name,CPU_REQ:.spec.template.spec.containers[*].resources.requests.cpu,CPU_LIM:.spec.template.spec.containers[*].resources.limits.cpu'
kubectl get sts  -n <ns> -o custom-columns='NAME:.metadata.name,CPU_REQ:.spec.template.spec.containers[*].resources.requests.cpu,CPU_LIM:.spec.template.spec.containers[*].resources.limits.cpu'
```

当时摸底结果：全集群 JVM 清一色 request 200~300m / limit 0.3~0.4 核（assist 400m、auth 300m、produce 350m——比出事时的 mobile 还紧），系统性偏紧，mobile 只是流量倾斜后第一个痛的。定调**批量治理**，不逐个修。

## 7.4 治理定价公式

拿第 6 节 cpuacct.usage 差分 + 高峰期观察的峰值用量：

- `limit ≈ 峰值均值 × 3~5`
- `request ≈ 峰值 × 1~1.5`
- limit 不占调度容量（超卖无碍），request 占——所以放宽 limit 零风险、放大 request 要看节点余量

当时终局：assist/auth/produce req 500m + limit 4；basic/device/home/order/quality/report/technics/mold limit 2、request 原样；差分全部归零收口。

## 7.5 变更红线（fobrite 生产环境实测）

- **txmanage（事务协调器）、spring-gateway 网关属基础设施，配额再紧也不进批量清单**——gateway 重启会级联全服务重启（探针疑似经网关探活）。
- 批量 `set resources` / `scale` 的清单生成后，**人工过一遍排除项**再执行。
- `kubectl top` 报 heapster NotFound + `deployments.extensions` API 组 = 集群版本老（≤1.15 量级），metrics-server 选型先查兼容矩阵再装。

# 8. 速查表

```text
症状：容器慢 + 宿主机闲 + 线程全 R 态单线程 %CPU 低
  → cat cpu.stat，算 nr_throttled/nr_periods
    ├─ 明显（>1%）→ CFS 限流实锤
    │    → cat cfs_quota_us 确认配额
    │    → cpuacct.usage 差分测真实用量
    │    → set resources 放宽（req+lim 一起写）
    │    → 高峰期差分循环验收增量=0 + p95/p99 同钟点对比
    ├─ per==0 → 无配额档，不是异常
    └─ 正常 → 转向 GC/下游/锁等常规排查
验收：跑满业务高峰，不是发布后十分钟
告警建议：throttled 周期占比 >1% 持续 5 分钟
```

一句话版：**request 决定放不放得下，limit 决定跑不跑得快，突发形态决定用户体验——三本账各记各的。**
