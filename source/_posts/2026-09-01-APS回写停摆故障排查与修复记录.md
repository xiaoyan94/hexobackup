## 现象与结论

生产环境登奇 MES 对 APS 的工单状态回写自 8 月 30 日起停止：`sync_aps_fail_log` 无新增记录（此前每天 4000+ 条），APS 侧收不到任何推送数据。MES 业务功能（开工/报工/结单）不受影响，应用日志无报错。

结论：APS 推送的 HTTP 工具方法未配置超时，8 月 30 日一次瞬时网络异常后，10 个推送工作线程永久阻塞在 socket 读取上，线程池占满，后续推送任务在无界队列中积压，不再执行也不再产生失败记录。重启服务恢复。修复已提交 r33441。

## 推送链路与代码位置

调用方共两类，全部汇聚到同一个单例 Service：

| 调用方 | 位置 |
| --- | --- |
| 定时任务（每 10 分钟推未完工单） | `APSMesOrderPushTask.pushMesOrderStatus` |
| 业务事件（开工/暂停/报工/结单/强制结单） | `ProduceService`、`FlowOrderStatusService`、`OrderStart*/OrderEnd*/OrderBreak*/OrderPause*` 等 8 处 |

执行链：

```
APSMesOrderPushService.pushMesOrderStatus          (APSMesOrderPushService.java:81)
  └─ CompletableFuture.runAsync(..., executorService)   executorService = newFixedThreadPool(10)  (:35)
       └─ HttpUtils.postByJSONArray(postData, apsServer + "/api/mesManufactureState")
            └─ HttpClients.createDefault() + client.execute(httpPost)   ← 未设置任何超时
       └─ saveApsApiFailLog(...)                       失败时写 sync_aps_fail_log
            └─ doSaveApsApiFailLog → CompletableFuture.runAsync → bizCommonService.simpleInsert
```

三个代码事实构成故障面：

1. `HttpUtils.java:130`（utils 公共模块）：`HttpClients.createDefault()` 未设置 `RequestConfig`，connect/socket 超时为默认值 0，即无限等待；
2. `APSMesOrderPushService.java:35`：`Executors.newFixedThreadPool(10)`，固定 10 线程 + 无界队列，无拒绝策略；
3. `APSMesOrderPushService.java:147`：失败落库外层 `catch (Exception e1) { // do nothing }`，异常静默。

## 排查过程

按以下顺序取证，每步一个结论：

**1. 数据侧确认停摆时点**：`sync_aps_fail_log` 按 `date(createtime)` 统计，8 月 30 日起归零，此前 6 天日均 4000+。

**2. 日志分层区分故障层**。同步层日志（调度线程打印）与异步层日志（工作线程打印）的存亡组合可以直接定位故障层：

| 检查项 | 命令（pod 内） | 结果 |
| --- | --- | --- |
| 任务启动 | `grep -c "APSMesOrderPushTask.pushMesOrderStatus start"` | 4 次，正常 |
| 任务完成 | `grep -c "...pushMesOrderStatus end"` | 4 次，与 start 一致 |
| 逐单循环（同步） | `grep -c "...mesorderno:"` | 129 次（约 32 单/次），正常 |
| HTTP 请求（异步） | `grep "HttpUtils::post uri"` | **0 次** |

同步层全部正常、异步层为零，说明推送任务已提交但异步体从未执行，问题在线程池。若循环日志也为零才是查询条件/数据问题。

**3. 线程栈确认**（pod 内无 jstack/jcmd，用 SIGQUIT，栈输出到 stdout 经 `kubectl logs` 收集）：

```
"pool-9-thread-1" ~ "pool-9-thread-10"  共 10 个，全部 RUNNABLE
    at java.net.SocketInputStream.socketRead0(Native Method)
```

10/10 线程阻塞在 `socketRead0`，即线程池被挂死连接占满。

**4. 对端状态**：从 pod 内 curl APS 接口（`aps.server` 配置值），秒回业务响应，对端当前正常。

**5. 进程启动时间**：`ps -ef`，进程 8 月 6 日起未重启。

第 3/4/5 步合起来定性：8 月 30 日瞬时网络异常使当时在途的 10 次调用永久挂起；因无超时，线程不随对端恢复而释放；只有重启能恢复。

## 修复内容（r33441）

**HttpUtils.java**（utils 公共模块）——`post` 与 `postByJSONArray` 增加 RequestConfig，写法与同类 `getByToken`/`postByToken` 一致：

```java
private static final int CONNECT_TIMEOUT = 3000;
private static final int SOCKET_TIMEOUT = 10000;

// postByJSONArray / post 方法内：
httpPost.setConfig(RequestConfig.custom()
        .setSocketTimeout(SOCKET_TIMEOUT)
        .setConnectTimeout(CONNECT_TIMEOUT)
        .build());
```

**APSMesOrderPushService.java**——两处 `catch (Exception e1) { // do nothing }` 改为记录 error 日志（`:147` 与 `saveApsApiFailLog(Exception)` 重载内各一处）。

修复后的失效路径：对端半死 → 线程至多 13 秒超时释放 → `postByJSONArray` 返回 null → 走既有失败分支写 `sync_aps_fail_log`（error=接口返回数据为空）→ 线程池自愈。

## 本地验证

用只接受连接、永不回包的 TCP 端口模拟对端半死（python 起一个 accept 后挂住的 listener），dev 环境把 `aps.server` 指向它，通过 `POST /feign-api/Produce/pushMesOrderStatusPullDown`（`ProduceRestController.java:387`）触发推送：

| 场景 | 结果 |
| --- | --- |
| 修复前（.m2 旧 jar） | 请求发出后无任何后续日志，线程挂死——本地复现生产故障 |
| 修复后（单次触发） | 请求发出后精确 10.08s 出现 `SocketTimeoutException: Read timed out`，线程释放 |
| 修复后（连续 16 次） | 16/16 全部超时返回，两轮周期内排空，队列无积压 |
| 失败落库 | dev 库 `sync_aps_fail_log` 产生 16 条记录，error=接口返回数据为空 |

验证时注意：本地按模块启动时公共模块从 .m2 解析，改 utils 后需先 `mvn install -pl springboot/common/com.zhiyin.mes.common.dengqi.utils -P central,dev` 再重启业务模块，仅 compile 不生效。

## 影响范围与发版注意

1. `HttpUtils.post` 同样加了超时，调用方包括：auth 的 `QamslinkController`、mobile 的 `WeChatAuthController`/`SnmsApiController`（微信/SNMS 取 token）。行为变更：此前无限等待的调用现在最多 13 秒后返回 null，调用方均已按 null 失败分支处理，无适配成本。
2. alert 模块存在一份独立的 `com.zhiyin.service.utils.HttpUtils` 拷贝（微信小程序消息发送用），`post` 同样无超时，本次未改，后续可同步处理。
3. utils 为公共模块，produce/auth/mobile 随各自下一次发版生效。

## 遗留事项

1. 停摆期间（8 月 30 日至恢复）结单/强制结单工单的终态推送已丢失且无失败记录可自动重试（retry 任务只扫 `sync_aps_fail_log` 且仅限 osDone/osTerminate、2 天窗口），已按 `biz_order_child.endtime` 盘账生成补推脚本执行；
2. APS 日常批量拒绝推送（返回 1003「MES工单号不存在」，日均 4000+ 条），为停摆外的存量问题，待与 APS 方对账；
3. 可考虑增加反向监控：在制工单数 > 0 且 `sync_aps_fail_log` 长时间零增长时告警，覆盖此类归零型故障。
